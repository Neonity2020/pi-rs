# 06 可靠性与数据完整性

> 来源：官方 `docs/003-execution.md`（Stored work 一节）、`docs/007-architecture.md`（Effects/Store/Persistence），对照 `src/app/effects.ts`、`src/app/store.ts`、`src/app/delivery.ts`、`src/app/outbox.ts`。
> 设计立场：**引擎永不阻塞**——所有端口调用（Executor/Assessor/Outbox）只把工作**排队**；真正的等待全部由持久化效果队列承担。系统崩溃在任意点重启后都能收敛。

## 1. Effects：持久化副作用队列

**先存储，后执行**（stored work）：把候选/跟进/报告 relay 给主会话、启动 Assignment、投递 Input、回复渠道——全部先落库再由队列执行。

| 机制 | 说明 |
| --- | --- |
| 每 kind+key 一行 | 同 key 重复入队**替换 payload** 并提前到期，不改队列顺序（合并去重） |
| 提交后才执行 | `enqueue` 在 Engine 事务内调用；事务回滚则效果不存在 |
| `Later` 异常 | "暂缓"不计失败预算（如无空闲槽位时稍后再试） |
| 失败退避 | 各 kind 自有区间（见下表）；连续失败 ≠ 死循环 |
| 健康条目 | 每 kind 一个；**连续 3 次失败**才报 error（一次性网络错误不足为惧） |
| 有序类 | `relay`/`notice`/`reply` 并发=1；一条失败会压住同 kind 后续（保持顺序） |
| 停机 | `drain` 停止处理但保留待执行行 |

| kind | 执行者 | 并发 | 重试 |
| --- | --- | --- | --- |
| `assessment` | MasterAssessor：把 Eval 候选卡 steer 进主会话回合 | ≤4（暂停时不投） | 2s→60s 翻倍 |
| `launch` | DshExecutor：prepare→建会话→首条任务消息 | 空闲 worker 槽数 | 瞬态 3 次 5s→300s；其他失败/prepare 失败 ⇒ 票 failed；等槽/暂停 5s 再试 |
| `delivery` | DshExecutor：按序投递待发输入 | ≤4 | 2s→60s；等槽 2s 再试 |
| `relay` | Sessions：worker 报告/提问/人类跟进 steer 进主会话 | 1（有序） | 2s→60s |
| `notice` | Sessions：向主会话注入通知（不唤醒） | 1（有序） | 2s→60s |
| `reply` | Outbox：经 Source 发渠道消息（同票同会话有序） | 1 | 5s→300s；Source 停用/被压住 5s 再试 |

**generation 计数器**：一行在执行中又被重新入队时不会互相覆盖（`src/app/effects.ts:134`）。

## 2. Passes 心跳

- 2 秒间隔 + 命令按需触发；**单飞 pump**：pass 运行期间被请求的 pass 合并为一个尾随 pass；
- 一个 pass = 处理到期效果 + `engine.evaluateDue()`（对每个 Eval/Ticket 用独立事务，逐实体幂等）；
- Source 的 Trigger 经 `receive` 入库后由 pass 驱动后续一切；故障的 pass 在 `runtime` 健康条目上报。

## 3. 幂等性清单（每个可能重放的点都有对策）

| 危险点 | 对策 | 出处 |
| --- | --- | --- |
| Trigger 重复入库/重复 accept | 内容寻址确定性 id（sha256）+ 收到即去重；GitHub 用评论 id+`updated_at`，飞书用 message id | `src/core/ids.ts`、`intake.ts` |
| 渠道消息重复发送 | Outbox 回执表（id 永不二次入队）；发送携带幂等键（GitHub 隐藏 HTML 标记、飞书幂等键、cookbook 要求 `--key`） | `outbox.ts`、`github-channel.ts` |
| 对 DSH agent 的消息重复 steer | `AgentDelivery` 按 requestId 至多一次，跨重启由持久会话历史 + 收件箱扫描判定 | `delivery.ts` |
| 效果行重放 | generation 计数器 | `effects.ts` |
| 重复唤醒/重投输入 | 投递前复查票活性；重启后清走会话内残留副本再投新 Assignment | `dsh.ts` |
| 轮询游标 | 游标仅在**全部覆盖的 Trigger 已入库后**推进；中断的轮次游标不动 ⇒ 重放安全；时间游标回退 5s | `poll.ts`、cookbook |

## 4. 事务边界

- `Engine` 每个命令一个事务（`repo.atomic`）；跨部件命令（attach、evaluateDue、policyChanged）按序多次小事务；
- **端口调用在事务内入队、提交后执行**——不会出现"事务回滚但外部世界已被改动"；`stop` 这类取消用 `Store.afterCommit` 保证回滚时不误伤；
- `afterCommit` 语义：只在提交后运行，回滚绝不运行；
- 测试侧 `MemoryRepositories`（`src/core/memory.ts`）复刻同样的嵌套回滚，保证领域规则在内存与 SQLite 上一致验证。

## 5. 故障恢复矩阵

| 故障 | 检测 | 恢复 |
| --- | --- | --- |
| 模型/网络瞬态 | 408/429/5xx、ECONNRESET 等 | launch 3 次退避重试；失败 turn 收续跑消息；`RetryHealth` 被动探测 `budget_exceeded`（模型预算重试）在 `models` 健康条目展示，**不改变**模型或重试策略 |
| prepare 失败 | 输出记录在票上 | 票 failed；修复命令后 retry 或人消息重触发 |
| Input 投递失败 | delivery 效果重试 | 票进入 `person/delivery` 阶段（面板可见、可 retry） |
| 渠道不可达 | reply 重试 5s→300s | 永久不可达（410/删除/锁定/撤回）⇒ `dropped` 并保留原因；Source 停用则等待 |
| Source 轮询失败 | 每 Thread 独立 `pollError`；连续 3 轮失败才报 Source error | 下一轮重读；通知对象失败读 24h 后放弃；读位置不前移 ⇒ 后续能补读漏掉的内容 |
| 主机重启 | 启动时 `executor.resume()` | 运行中 Assignment 按最老票优先重启 + 恢复便签；未取走输入重投 |
| 处理暂停 | `paused` 设置 | 恢复后 deadline 平移、等待恢复的票在首个 pass 恢复 |
| 无效配置 | 启动校验 | Source 实例禁用；未知配置键拒绝启动并指认键名 |

## 6. 健康体系（HealthBoard）

每条目唯一写入者；`starting → ready → error`（各自的下一次成功清除）：

| 条目 | 报告者 | 含义 |
| --- | --- | --- |
| `runtime` | Runtime（Passes 代报） | 应用自身/心跳故障 |
| `models` | Sessions | 会话等待模型预算重试 |
| `evals` | Runtime | 最近一小时未解决的 unavailable Eval |
| `assessment/launch/delivery/relay/notice/reply` | Effects | 各类存量工作（delivery 的失败显示在其票上） |
| `worker` | DshExecutor | Executor 会话事件处理（首次失败后出现） |
| `github`/`feishu`/`history` | SourceRegistry | 轮询、事件、历史恢复 |
| `sync:<id>` | Settings | 允许名单同步（失败 1 分钟起翻倍至 1 小时重试） |

## 7. 迁移与兼容

- schema 版本只增；**schema 11** 由 `migration.ts` 一次性从 schema 10 升级（旧主会话 relay/退订队列并入 effect 表、pending `reopen` 输入转 text）；
- 更新版本的库拒绝旧版打开 ⇒ 升级前必须备份 `<stateDir>/orchestrator.sqlite`；
- schema 10 之前的库直接拒绝（提示换新 state 目录）。

## 8. 已知的可靠性债务（官方明示）

1. **无界增长**：trigger/disposition/decision、已结束票、outbox 回执、settings/prompt 历史版本——尚无清理/归档机制；长期运行需外部归档或等待官方方案；
2. **内存缓存丢失**：TextCache/链接缓存重启即失，会话翻页需从 offset 0 重读；
3. 发布版为研究代码：官方声明可能含 bug、工程实践不一致。
