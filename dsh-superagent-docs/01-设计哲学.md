# 01 设计哲学

> 来源：官方 `docs/000-philosophy.md`。这是理解全部其余设计的钥匙：**每一处看似繁琐的机制（观察模式、准入表、消息上限、面板留白）都是这条原则的推论。**

## 核心原则

**尽可能少占用人类注意力，尽可能多创造价值。**
（Take as little human attention as possible, and give as much value as possible.）

项目的每个部分都用它**消耗的注意力**来评判：一条消息、一个通知、一个问题、一项设置、一个面板元素、一段文档，各自都要"给出的价值大于消耗的注意力"，否则被删除。

## 对 agent 的推论（五条行为准则）

| # | 准则 | 在系统中的落点 |
| --- | --- | --- |
| 1 | **只在被要求时行动，或团队书面规则允许时行动** | 允许名单 + 准入表 + accept 三模式（off/observe/auto）；主动工作一律从 observe 开始 |
| 2 | **只在人必须行动或能用上结果时说话** | 确认一次并说明将做什么；工作中保持安静；结果就绪、需要决定、无法完成时才再开口；消息短、回原对话 |
| 3 | **一次只问一个具体问题**，以结构化形式提出 | Report 的 `attention` 字段：问题必须结构化（`human_action`），不允许藏在长报告的自由文本里 |
| 4 | **按影响停止，而非按努力停止** | 局部修改做到可审查为止；需要设计决定就带着清晰的问题停下（scope 规则：暂停条件） |
| 5 | **诚实汇报** | 草稿标 unfinished；失败报 `failed`；绝不为了不提问而绕过限制 |

## 对设计的推论（四条准则）

1. **少概念**。设计只有领域概念（Source 等）及其实例（GitHub、飞书）。新业务需求要么成为某个概念的**属性**，要么成为 agent 遵循的**提示词**，不新增概念——官方在 `docs/001` 里维护了一张"被拒绝的概念"表来强制这一点（见 [02 领域模型](02-领域模型.md)）。
2. **少设置**。一个默认值能适合几乎所有团队时就不设配置项；团队想用自然语言描述的行为是**提示词文本**而不是设置（例如合并策略写在 Delivery requirements 提示词节，宿主没有任何 merge 决策逻辑）。
3. **面板只显示需要人的东西**。等待人的事项列在最前；健康状态不占空间。
4. **文档按序阅读**。每个编号文档只建立在此前文档引入的概念之上；`tests/docs.spec.ts` 甚至用测试强制"只能引用更早的文档、链接必须可解析、表格索引必须完整"。

## 对运营者的要求（责任）

Agent 以团队**每天都能看到的账户**发言、开 PR、给人发消息——它发出的每条消息都在消耗同事的注意力，**这是运营者的责任**。能力越大，运营者欠团队的谨慎越多：

- **从窄开始**：先用很短的允许名单 + 主动工作只记录不执行；观察到"它本会做的事"是对的，再放宽。
- **调优方向是减噪**：agent 吵的时候，把它的提示词改短改严，或暂停它；**不要**用"加更多解释性消息"来解释噪音。
- **不要用它刷量**：批量 PR、广播消息、busywork 的注意力成本高于其价值。
- **为它说的话负责**：读它以你的名义发的内容；它错了就改提示词。

目标一句话：**在正确的时刻给正确的帮助，其他任何时刻什么都没有。**
