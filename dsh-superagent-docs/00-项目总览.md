# 00 项目总览

## 1. 背景：从 Harness 到 Super-agent

| 时间 | 事件 |
| --- | --- |
| 2026-08-13 | DeepSeek Harness 工具包（DSH，agent 运行宿主）发布 |
| 2026-10-31 | DeepSeek Harness 团队发布论文《Exploring Super-agent Design: Towards a More Autonomous Agent System》，同日开源研究原型 **dsh-superagent-prototype**（MIT） |

命名里的 **super-** 不是"超级"，而是 **"above"（在其之上）**：一个位于其他 agent 之上、更自主的**协调层（coordination layer）**。论文的核心论断是：

> 编码 agent 的真实瓶颈不是模型能力，而是**人类注意力**——一个能替整个团队干活的 agent，同样能消耗整个团队的注意力。

因此 Super-agent 的目标被定义为四个特征：**连续、高效、主动、持久**——让 AI 可 7×24 小时在线、跨平台接收指令，而人类只在"必须行动"或"能用上结果"的时刻介入。

## 2. 产品形态

dsh-superagent 是一个面向**单个 GitHub 仓库**的 proactive coding agent，打包为 DeepSeek Harness 的 **bundle**（插件集，基于 cordis 框架）：

- **接入**：监听 GitHub（Issue、PR、评论、CI），可选接入飞书群聊；
- **触发**：允许名单里的人 `@` agent 专用账号提出具体请求（或符合团队自写规则的"推断候选"）；
- **执行**：路由为一个内部 Ticket，每个 Ticket 在**自己的 worker Session + 独立工作目录**中运行；
- **交付**：回到原对话交付结果，通常是 **Pull Request**（由人来审查合并）；
- **监督**：Web 面板只显示"需要人的事"。

关键约束：

- 主会话（Router）**不写代码**，甚至被刻意限制为"没有 shell 也能运转"，防止它越俎代庖；
- Worker **从不直接接触人**，只向主会话汇报——人类面对的是**单一声音**；
- 主动的（无人请求的）工作默认只**记录"我会做什么"**（observe 模式），经团队审阅后才允许自动执行。

## 3. 技术形态

| 维度 | 事实 |
| --- | --- |
| 语言/构建 | TypeScript、pnpm、tsdown、vitest（`pnpm check` = 类型检查 + 测试 + 构建） |
| 宿主 | DeepSeek Harness（`dsh` CLI，cordis 插件框架），以 bundle + `cordis.patch.yml` 插入三个插件（主插件、github-watch、feishu-watch[默认停用]） |

## 4. 一次典型交互（从 @ 提及到 PR）

1. **接入**：GitHub 轮询（默认约 1 分钟一轮，遵守 `X-Poll-Interval`）读到一条评论 `@agent 请在 README 加 Quick Start 一节，只改 README，开 PR，不要合并`；
2. **入库**：翻译为不可变 **Trigger**（确定性 id），入库去重；范围过滤（`scope`）通过后挂到其 **Thread** 上；
3. **门控（Gate）**：发送者在允许名单 + 直接 @ agent ⇒ **explicit（明确）**强度，免研判直接成为路由候选；
4. **路由**：主会话用 `orchestrator_route` 做 **accept** 决定 ⇒ 原子地创建 **Ticket** + 不可变 **Mandate**（记录策略版本、匹配规则、发送者身份）+ 首个 **Assignment** + 对该 Thread 的**订阅** + 确认回复；
5. **启动**：DshExecutor 预留 worker 槽位 → 运行 prepare 命令（典型为 `git worktree` 建检出）→ 创建 `worker-<ticketId>` 会话 → 下发首条任务消息（正文截 1500 字符 + read 指针）；
6. **执行**：worker 先 `orchestrator_ack` 确认 → 实施 → 交付 PR → `orchestrator_report progress/ready`（带 `pr_number`）绑定 PR 线程；GitHub Source 观察到 PR 合并/关闭 ⇒ Ticket 以 `merged`/`closed` 终结；
7. **交付**：回复经 Outbox 按会话顺序送达原对话；所有 GitHub 消息以固定声明开头（"This is by an automated agent, not a human."）；
8. **监督**：全程仅当 worker 提问（attention）或交付就绪时，人才需要在面板/对话里出现。

## 5. 与论文的关系

官方 README 明确三点差异声明：

1. 发布代码源自团队日常开发，大量工程由 coding agent 完成，**可能含 bug、风格不一**；
2. 发布版为公开而改写，**不等于内部版本，也不等于论文实现**；
3. 论文中的部分设计（如长期记忆、BYOM 级别的环境解耦）在原型中**尚未实现**，属未来方向。

论文侧的关键设计思想（原型中的对应物见括号）：

- **Router/Worker 双层调度**（主会话/worker 会话）——解决"全进一个 Session 会串行且互相污染、每事件新开 Session 又缺全局上下文"的两难；
- **上下文当缓存用**：先给 id + 短摘要，可能用到的给全文，长材料截断藏在指针后（原型：inline/spill + `orchestrator_read` 资源 + LRU TextCache；借鉴操作系统 Page Cache 的 Inline/Spill 思想）；
- **事件两级过滤**：先纯代码过滤、再模型按规则研判（原型：Source `scope` + Gate 准入 → Assessment 研判）；
- **"静默复现并修复"**：后台尝试复现 bug，确认修复才开 PR，否则用户什么都听不到（原型：`dropped` 报告——静默终结）;
- **计算与状态分离 / BYOM**（接入自有开发机、云端托管机器；据媒体对论文的报道，原型内执行仍发生在 DSH 宿主内）。

## 6. 快速上手（部署视角摘要）

完整步骤见 [09 部署与运维](09-部署与运维.md)；流程设计为**由 coding agent 陪同人类完成**（`SETUP.md` 是给 agent 的脚本）：

```sh
npm install -g @deepseek-ai/dsh@0.2.1-rc.3
git clone <this repository> dsh-superagent && cd dsh-superagent
pnpm install && pnpm build
dsh superagent --from-default-profile web --dump-config > /dev/null   # 建独立 profile
dsh plugin --profile superagent add "link:$PWD"                        # 安装 bundle
scripts/dsh-superagent start && scripts/dsh-superagent status          # 启停
```

之后按顺序配置：**Sources**（仓库 + agent CLI）→ **Policy**（允许名单）→ **Execution**（目录根 + prepare 命令）→ **Prompts**（团队三节）。首启默认 `observe` 模式、非自动合并；先用练习仓库跑通再加真实凭据。

## 7. 论文实验数据摘要（转引自解读文章，供参考）

| 指标 | 数值 |
| --- | --- |
| 测试规模 | 每轮约 300 条消息（其中约 20 条真实工作请求），编码以耗时工具模拟 ⇒ 度量的是调度而非代码质量 |
| 任务完成时间 | super-agent 平均 12.4 分钟（最差 15.7）vs 单会话基线最差 29.5 分钟 |
| Router 扩展性 | 负载从约 1 升到 40 决策/分钟时，事件批处理后单决策耗时从 6.4s 降到 1.6s |
| 成本 | 单轮消耗 23.2M 缓存读 token（无 pass-through 优化为 31.8M），淡季定价约 $7——架构偏好廉价模型 |
| 委托提示词实验 | 中性提示（"需要时用 sub-agent"）5 轮 0 次委托；强提示 4/5 ⇒ **委托必须是结构属性**（独立会话、移除工具、强制边界），而非提示词措辞 |

> 注意：这些数字来自论文/媒体报道的转述，非本仓库可复现的基准；仓库内亦无 benchmark 代码。
