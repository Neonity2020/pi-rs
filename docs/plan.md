# 计划

> 状态日期：2026-10 · 版本：0.2.1
> 这份文件是项目级路线图。单次任务的临时步骤写在根目录 `PLAN.md` / `TODO.md`，完成后吸收进这里或删除。

## 现在在哪

核心闭环已完成并可用：

- 四工具 agent 循环、无 max steps；工具按序执行并逐项报告，取消后跳过剩余调用；Unix bash 取消/超时清理进程组内后代。
- SSE 完整性：必须有 finish_reason；工具必须以 tool_calls 结束，截断响应报告错误、保留正文且不执行工具；支持逐字节分块与省略 DONE 的完整响应。
- 资源边界：read 按范围流式读取，bash 有界保存头尾并持续排空管道；二者结果最多 64 KiB。连接 10 秒、读取空闲 120 秒超时；SSE 单行最多 1 MiB，API 错误正文只收集前 2,000 字节。
- CI 已配置：Linux/macOS 检查格式、Clippy、锁定依赖测试/构建及 PTY 冒烟；Node 24 检查网站 npm ci/build。远端结果以实际 workflow 运行为准。
- 三种模式：交互 TUI、print、JSONL。
- 会话 JSONL 追加写、活动分支恢复；损坏末行先完整备份再修复，中间坏行与损坏父链明确报错；落盘失败取消回合并阻止继续使用失配的历史。
- DeepSeek（思考模式/强度/峰谷成本）+ 任意 OpenAI 兼容端点。
- 登录：`pi login` / TUI `/login` 验证 key 后写入 `~/.pi-rs/auth.json`（0600）；`/logout` 删除。
- TUI：Markdown、表格、代码块行号与语法高亮、鼠标滚动与跟随、Ctrl+V 粘贴剪贴板图片；输入 `/` 弹出命令列表，↑↓ 选择、Tab 补全；推理与工具调用折叠成可展开的思考块（结束时显示「思考结果」）。
- 上下文压缩：请求前按窗口阈值自动总结旧消息，overflow 时压缩重试一次；`/compact` 手动触发；摘要作为 `compaction` 记录落盘并可 `-c` 重放。
- 长期记忆：全局 / 项目两个 Markdown 文件，启动时有界注入；`/remember` / `/forget` / `/memory` 管理；不自动抽取。
- 实验模式：`/lab` 开启；`/dream` 用一次隔离的模型回合合并、保留、遗忘长期记忆，内部回合不进会话。
- 测试：231 个单元/端到端测试 + 两个 PTY 冒烟脚本；e2e 不需要真实 key，覆盖连续恢复与落盘失败后的工具阻断。
- 文档：目标、架构、计划、开发指南。

## 候选池

按“用户痛感 × 实现成本 × 是否破坏极简”排序。**未承诺**，取用前先在 issue / `PLAN.md` 写清触发条件。

### 1. 会话分支导航

- **问题**：JSONL 已是树，但 `-c` 只走最后一个活动分支；用户无法回到旧分支继续。
- **触发**：出现“想从三天前那次会话分叉”的真实需求。
- **最小方案**：列出当前 cwd 的会话与分支点，`--session <id>` 选定 tip；不改文件格式。
- **验收**：旧会话可恢复且新消息的 `parent` 正确；原有 `-c` 行为不变。
- **风险**：TUI 选择器会把 `coding` 变重；优先命令行参数。

### 2. TUI 会话内搜索

- **问题**：长会话只能滚轮翻。
- **触发**：单次会话渲染超过约 1–2 千行、定位成本明显。
- **最小方案**：`/` 进入搜索，只高亮当前匹配，不引入模糊查找库。
- **验收**：不破坏输入框与滚轮；无匹配时明确提示。
- **风险**：键位冲突；渲染层可能被迫理解“搜索状态”。

### 3. OpenAI 模型与成本

- **问题**：`--provider openai` 可用，但模型注册表只有 DeepSeek，成本显示 `-`。
- **触发**：有人实际用 OpenAI 兼容端点并关心成本。
- **最小方案**：在 provider 层加最小模型表（id、窗口、单价）；未知模型继续不估价。
- **验收**：已知模型显示估价，未知模型行为不变；不引入在线价格查询。
- **风险**：价格会过期；需要标注数据日期。

### 4. 渲染性能

- **问题**：每个 dirty 帧重算整段 transcript 的 Markdown。
- **触发**：数万行会话出现可感知卡顿。
- **最小方案**：按 `App::version` / 消息项缓存已渲染行，只重算尾部。
- **验收**：滚动与流式输出均不掉帧；缓存失效条件有测试。
- **风险**：缓存把 TUI 的状态机变复杂；没到阈值不做。

### 5. 跨平台收尾

- **问题**：`bash` 工具、路径与 shell 假设偏 Unix；Windows 未验证。
- **触发**：有 Windows 用户。
- **最小方案**：明确文档化为 Unix-first；或在 `bash` 工具内做平台分支。
- **验收**：至少一份 CI/本地验证记录；不引入平台抽象层。
- **风险**：容易演变成“支持所有 shell”，违背极简。

## 明确不做（当前）

与 [goals.md](goals.md) 的“不要什么”一致：plan mode、内置 todo、sub-agent、MCP、后台 bash、权限弹窗、动态插件、Web/云/多用户。

另外现在也不做：

- 分支压缩 / branch summary——当前没有树形会话导航，等有真实需求再加。
- 遥测与远程日志——本项目的调试信息就在会话文件与 `--json` 里。
- 配置文件的多层合并——参数 + 环境变量 + `.env` 已经够用。
- 自动记忆抽取 / 向量检索——长期记忆是用户显式维护的 Markdown；`/dream` 只在用户手动触发时运行，不做后台抽取。改变这个决定先改 [goals.md](goals.md)。

## 开放问题

1. `-c` 的“最近会话”是否需要感知分支，还是永远取最新文件的活动 tip？
2. OpenAI 兼容端点是一等公民，还是“能跑就行”的兜底？
3. 峰谷成本是否值得补中国法定节假日，还是保持量级估算？
4. 代码块语法高亮要覆盖到什么程度？当前是小型分词器，不为新语言引依赖。

开放问题的处理方式：有真实使用证据再决定，不在文档里假装已经决定。

## 工作方式

1. 接到需求，先对照 [goals.md](goals.md) 的自检清单。
2. 写入 `PLAN.md`（目标、步骤、验收），`TODO.md` 跟踪进行项。
3. 实现 + 测试；架构不变量有变化就同步 `architecture.md`。
4. 完成后更新本文件的状态/候选池，删除临时 `PLAN.md` / `TODO.md`。
5. 提交信息说明“为什么”，不只是“改了什么”。
