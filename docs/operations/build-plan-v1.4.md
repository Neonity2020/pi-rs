# Rust 版 Pi Agent 全面构建计划 v1.4

日期：2026-10-28。本地上游各包声明版本为 1.4.0；其提交尚未验证为某个发布 tag。目标是以固定的上游快照为参照，交付可验证的 Rust 实现；功能等价由逐项契约和测试证明，不以代码行数或 crate 数量衡量。

## 基线与范围

- Rust 仓库 HEAD：`c26d4b4`；工作区存在未提交的 agent loop、session、RPC 和 context usage 改动，实施前须审阅并保留，不能当作已验收功能。
- 本地上游 `pi/`：`f9daca3480732d0042b1df3a6e27221f597a620d`，浅克隆；各包版本均为 1.4.0，本地无对应 tag；发布 tag 身份待核实。启动时记录完整 SHA、包版本、许可证及协议版本，固定为对照基线；变更基线须重跑差异审计。
- 已有 Rust 工作区覆盖 AI、agent、coding-agent、TUI、MCP、env 等；OpenAI 兼容及 Anthropic 流、内置工具、JSONL 会话、手动压缩、stdio MCP、部分 RPC 已有实现和测试。README、上游映射和 TASKS 的状态存在滞后或互相矛盾，应以代码与测试为准。
- 全面范围包含上游对应包的公开行为、CLI、交互、协议、扩展及外围能力。Rust 内部架构可不同；任何不兼容或平台差异必须列入兼容矩阵并由维护者明确接受，不能以桩实现或静默降级充数。

## P0：冻结契约和建立可复现基线

1. 以本地 1.4.0 包快照为工作基线；若要求特定发布 tag，核实其 SHA 并重新盘点。建立上游包、公开 API、CLI 参数、事件、配置、会话格式和平台的逐项清单；每项标记未实现、部分、已验证或接受差异，并链接源码及测试。
2. 审查现有未提交改动与阶段五计划，记录其完成程度及依赖；确认会话关闭、故障恢复、进程退出及消息顺序。保持 `pi/` 等参考目录只读。
3. 在干净隔离的测试环境运行 `cargo test --workspace --locked`、`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets --locked -- -D warnings`，记录平台、工具链、结果和失败；检查 CI 与 README 的实际状态，不沿用历史测试数量作为现状。
4. 搭建固定上游的差分测试框架：共享输入 fixture，分别执行 TS 与 Rust，归一化时间、随机 ID 等非语义字段，比较请求、事件顺序、退出状态及持久化结果；记录每个测试的上游 SHA。

**退出条件：** 兼容矩阵覆盖全部上游公开能力，基线和当前工作区状态可追溯，阻塞项有负责人。发布 tag 尚未核实时，不宣称与特定发布构建完全兼容。

## P1：核心运行时与持久化

- 完成 agent loop 的请求准备、工具前后及轮次钩子，定义并发工具执行的顺序、steering/follow-up、取消、重试和错误传播语义；对照上游处理边界情况。
- 完成 session 树、分支、切换、恢复、压缩及导入导出。实现自动压缩、保留最近上下文、溢出恢复和中途检查；明确写入、同步失败及崩溃后的实际保证。
- 完成七个工具的参数、截断、流式输出、超时和取消契约；验证文件修改、进程组及路径行为，并记录平台限制。
- 验收：差分测试覆盖多轮工具、取消与队列、分支恢复、压缩后再次恢复；故障注入覆盖部分写入、同步失败、进程退出与重试，不丢失或重复已确认的事件。

## P2：模型、认证与协议

- 逐项对照并实现上游 provider/API、模型目录、兼容参数、流事件、thinking、多模态、usage、错误和取消；以固定目录和配置格式为准，不将已有两个 provider 外推为全部完成。
- 实现配置层级、凭证解析及上游支持的认证/OAuth 流；密钥不进入日志、fixture 或错误输出。真实服务验证使用显式配置和独立测试账号，离线测试不依赖密钥。
- 完成 RPC 命令、响应、异步事件及错误帧；覆盖 session 操作、bash、图片及扩展交互等清单中的能力。
- 完成 MCP 所需的传输、生命周期、通知、错误、配置合并、信任和认证，依据冻结的协议版本建立兼容测试；项目配置执行命令前处理信任边界。
- 验收：本地 HTTP/SSE 和真实或参考服务契约测试覆盖分片、断连、取消、超时与错误；RPC 使用上游客户端/fixture 双向验证；MCP 跑上游适用的 conformance 测试并记录版本。

## P3：产品体验与扩展

- 对照 CLI、print、交互模式、命令、快捷键、主题、Markdown、选择器、编辑器、图片及终端行为逐项实现，修正现有文档中的能力冲突。
- 实现 skills、提示词模板、扩展发现和生命周期、事件与工具 API、包管理及配置。先用兼容性实验决定扩展宿主：若使用外部进程桥，必须证明现有上游扩展可运行；若不能，列为明确差异并解决，不能宣称完整兼容。codemode 的隔离边界和权限需单独验证。
- 验收：PTY 端到端测试覆盖启动、输入、流式渲染、选择器、终端恢复及异常退出；上游代表性扩展和配置 fixture 实际运行，含失败隔离与资源清理。

## P4：外围包与发布

- 按矩阵补齐 `pi-env` 远程环境、`pi-durable` 重放与持久任务、`pi-chord` 协作/RPC、`pi-telemetry` 和 `pi-codemode`；先定义与上游的公开契约、故障语义及部署边界，再分片实现。
- 补齐平台构建、安装、升级、配置迁移、故障诊断和用户文档；明确支持的 OS/架构及最低 Rust 版本。
- 验收：Linux、macOS、Windows 的 CI 和平台行为测试；远程环境、重放及协作提供可复现集成场景；发布包在干净机器安装并完成真实工作流。无法自动化的测试记录步骤、环境和结果。

## 执行顺序与交付管理

P0 → P1 → P2 → P3/P4；协议 fixture 和 UI 可在接口稳定后并行，但共享 session/agent 接口由单一集成者维护。现有阶段五计划作为 P1/P2/P3 的候选任务输入，先按 P0 审计其假设，再拆成独立可合并的工作项；各项写明范围、依赖、负责人、行为测试、验收证据和遗留差异。每阶段完成后更新兼容矩阵与文档，避免重复维护相互矛盾的进度表。

发布门禁：所有承诺范围的矩阵项均有通过的测试或经明确批准的差异；全工作区 fmt、clippy、测试及目标平台 CI 通过；完成上游差分、关键安全边界、性能基线、安装和恢复演练。明确列出未覆盖能力，不以 mock 测试代替真实服务或跨平台验证。工作量和日期在 P0 清单完成后按实际差距估算，避免虚假的排期承诺。
